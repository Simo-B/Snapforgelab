What I check

  • Supabase Row Level Security: your anon key is public by design, so if RLS is disabled or missing on a table, anyone can read or write it. I test which tables answer anonymous requests (read-only, I never touch your data).
  • service_role key in the frontend: the Supabase admin key shipped in your JS bundle, which bypasses every security rule.
  • Open storage buckets: public Supabase buckets exposing user uploads, invoices or private files.
  • Stripe keys and webhooks: secret keys in the client, unverified webhooks, checkout that never updates the database.
  • Auth redirect URLs: sign-up, magic link and OAuth redirects still pointing to a preview or lovable.app domain instead of your real one.
  • SEO of client-rendered SPAs: empty HTML for Google, missing titles and meta descriptions, no sitemap or robots.txt, every route returning the same page.
  • Hosting setup: Netlify, Vercel or Lovable hosting misconfigurations, like 404s on refresh, missing redirects, env vars and custom domain issues.

Is my Lovable app secure?

Not automatically: it depends on how your app is configured. If it stores data in Supabase, the anon key is public by design, so each table is only protected if Row Level Security is on with the right policies. The other common gaps are secret keys in the frontend, public storage buckets and auth redirects still pointing to a preview domain. I check all of these in the free audit, read-only, and send you the exact fix steps.

Is my Bolt app secure?

Not automatically: it depends on the configuration Bolt generated. If your app stores data in Supabase, every table needs Row Level Security with the right policies, secret keys must stay out of the frontend, and Stripe webhooks must be verified. I check all of these in the free audit, read-only, and send you the exact fix steps.
