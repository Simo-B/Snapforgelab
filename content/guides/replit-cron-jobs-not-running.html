Daily emails stop going out. The nightly sync ran Monday, skipped Tuesday, ran twice Wednesday. In the preview it worked perfectly. If the job is a setInterval, node-cron or APScheduler task inside your web server, the deployment type is the problem: Autoscale runs your server only while there is traffic.

Symptoms

  • Scheduled emails, reports or syncs run on some days and not others.
  • The job runs only after someone visits the app.
  • Jobs run twice when two instances are up at the same time.
  • Autoscale costs go up after you add a background timer.

Likely causes

  1. Autoscale scales to zero when idle, which stops any timer inside the process.
  2. Under load, Autoscale can run several instances, and each one runs its own copy of the timer.
  3. A busy timer keeps an instance alive longer, which costs compute.
  4. The job relies on in-memory state that is lost when the instance stops.

Step-by-step fix

1. Pull the job out of the web server

Move the job's logic into its own script, such as scripts/daily-digest.ts, that does the work once and exits. Remove the timer from the server code.

// scripts/daily-digest.ts
import { sendDigests } from "../server/digest";
await sendDigests();      // do the work once
process.exit(0);

2. Option A: Scheduled deployment

Replit's Scheduled deployments run a command on a cron schedule (for example 0 9 * * 1-5 for weekdays at 9am) in a time zone you choose, then stop. They have a job timeout, alert you when a run fails, and have no public URL. Set the run command to your script and give it the same database and secrets. A simple setup is a separate small Replit App for the job that uses the same production database.

3. Option B: a protected endpoint on a schedule

Expose the job as POST /api/cron/daily-digest, require a secret header, and have a scheduler call it. A request wakes an Autoscale app, so this works without changing deployment type.

app.post("/api/cron/daily-digest", async (req, res) => {
  if (req.get("x-cron-secret") !== process.env.CRON_SECRET) return res.sendStatus(401);
  await sendDigests();
  res.json({ ok: true });
});

4. Option C: Reserved VM for continuous work

Queue consumers, bots and anything that must run all the time need an always-on machine. A Reserved VM never sleeps and has a fixed monthly cost.

5. Make runs idempotent and visible

Store each run in a table (job name, started, finished, status). Before sending, check whether today's run already happened, so a retry or a double trigger does not email users twice.

Copy-paste prompt for Replit Agent

Open a new Agent chat (a fresh chat keeps old attempts out of its context) and paste this:

My background job (setInterval/node-cron) is inside the web server and does not run reliably on Replit Autoscale.
Please:
1. Move the job logic into a standalone script that runs once and exits, and remove the timer from the server.
2. Also expose it as POST /api/cron/<job-name>, protected by a CRON_SECRET header, returning JSON.
3. Add a job_runs table and make the job idempotent: skip if a successful run already exists for the current period.
4. Log start, end and the number of items processed.
Tell me what to configure for a Replit Scheduled deployment (run command, cron expression, time zone) as the next step.

How to verify the fix

  • The job_runs table has exactly one successful row per scheduled period over several days.
  • Calling the endpoint without the secret returns 401.
  • Triggering the job twice in a row does not send duplicates.
  • Scheduled deployment logs show each run and its exit status.
